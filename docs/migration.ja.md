# 移行と切り戻し

## pstack-codex v0.1.0 からの移行

[English](migration.md) · [クイックスタート](../README.ja.md)

nstack では `$poteto-mode` が `$natori-mode`、`$setup-pstack` が `$setup-nstack`、3件の `pstack_*` エージェント名が `nstack_*` になります。他の24件の名前は共通です。同じセッションで有効にする配布は一方に揃えます。

## 変更前に確認する

- `codex plugin list` で有効な `pstack-codex@<marketplace>` の正確な指定名と取得元を記録します。切り戻しに備えて v0.1.0 のチェックアウトを保持します。
- `${CODEX_HOME:-$HOME/.codex}/skills/` と `${CODEX_HOME:-$HOME/.codex}/agents/` に直接コピーしたものがないか確認します。旧スキル名2件、`pstack_{implement,security,review}.toml`、`pstack-codex-LICENSE*` が目印です。タグを持つチェックアウトでは `git ls-tree --name-only v0.1.0:skills` で旧スキルをすべて確認できます。
- プロジェクト領域にも配置した場合は確認対象に含めます。プラグインで有効なスキル、スキルのメタデータ名、エージェント TOML の `name` を照合します。ファイル名が異なっても宣言名は競合します。既存の `natori-mode`、`setup-nstack`、`nstack_*`、共通名のスキルは出所が判明するまで競合として扱います。無関係なファイルはその場に残し、曖昧な名前を解消してから進めます。

## 直接インストール

1. Codex セッションを閉じます。棚卸しで有効な旧プラグインが見つかった場合は、記録した正確な指定名で `codex plugin remove pstack-codex@<marketplace>` を実行します。切り戻し用に旧マーケットプレイスと取得元は保持します。スキルやエージェントの検索範囲外にバックアップ先を作り、v0.1.0 由来と確認したスキル、旧エージェント TOML 3件、旧ライセンス2件を相対パスを保って移します。編集済みスキルはタグの原本と比較し、バックアップした変更を新しい版に必要に応じて反映します。`babysit`、`autopilot-stack`、`session-pickup`、`pause-safely` では新しいプレイブック参照を維持します。
2. 新しいチェックアウトの [nstack インストール手順](../README.ja.md)で、対象スコープに配布一式を導入します。
3. 新しい `nstack_implement.toml`、`nstack_security.toml`、`nstack_review.toml` へ、対応する旧ファイルの `model` と `model_reasoning_effort` を引き継ぎます。意図的に省略していた項目は継承が続くよう省略し、ファイル名と `name` は新しい値を保持します。他のカスタマイズは個別に確認します。
4. 新しい Codex セッションで `$setup-nstack` を起動し、`$natori-mode` と `$setup-nstack` がそれぞれ1件、旧名が0件であることを確認します。モデルと推論強度を確認し、保存済みプロンプトも更新します。直接導入では Codex の設定と認証情報を維持します。

## ネイティブプラグイン

1. セッションを閉じ、記録した正確な指定名で `codex plugin remove pstack-codex@<marketplace>` を実行します。旧マーケットプレイスの登録と取得元は切り戻し用に保持します。直接コピーも併用していた場合は、上のバックアップ手順で検索範囲外へ退避します。
2. 保存した旧ソースとは別のチェックアウトまたは別のマーケットプレイスルートから、[新しいマーケットプレイスを登録し `nstack@nstack-local` を導入](skills.ja.md#その他の-codex-インストール方法)します。マーケットプレイスとプラグインの登録は Codex のコマンドで更新されます。
3. 旧 TOML と直接配置した旧ライセンスを退避し、新しい TOML を別途配置してモデル設定を移します。プラグインにはスキルとライセンスが含まれます。新規セッションで `$nstack:natori-mode` と `$nstack:setup-nstack` の検出とモデル設定を確認します。旧プラグインの名前空間を使うプロンプトも更新します。切り戻し後は復元した `pstack-codex:` 名前空間を使います。

## 切り戻し

セッションを閉じます。移行先がプラグイン導入なら `nstack@nstack-local` を削除します。**移行前**に旧プラグインを使っていた場合は、移行先が直接導入でも、記録した旧指定名を使って旧マーケットプレイスから再導入します。この移行専用の新しい登録が未使用なら削除できます。直接導入の場合は、新しいスキルを検索範囲外に移します。いずれの場合も、新しい TOML と直接配置した新ライセンスを退避し、バックアップを元のパスへ戻します。混在していた場合は旧直接配置分も戻します。新規セッションのスキル選択画面で復元したワークフローとセットアップを選び、モデル設定の復元を確認します。

## 直接配置・プラグインから管理スナップショットへ

当時の Python 版の手順は [v0.3.0 のコマンド集](v0.3.0.md)を参照してください。以前のスナップショットは切り戻し用に保持します。

[単体バイナリ](../README.ja.md)で新しいスナップショットをステージし、有効化します。ロール例はスナップショットの `examples/agents` に残り、既存のロール TOML は上書きされません。

旧版を直接コピーした環境では、既存の導入と並行して新候補を stage できます。一時ホームで候補を検証してから、旧スキルのディレクトリを検出範囲外に移動してバックアップし、新候補を有効化します。旧配置に戻す場合は管理シンボリックリンクを検出範囲外へ移し、バックアップを復元します。旧プラグインから直接導入へ移行する場合は、ソースとセレクターを記録してから旧プラグインを無効にします。切り戻しには元のセレクターを使います。

エージェント TOML はスキルと独立して管理します。v0.2.0 は `nstack_security` に Daybreak を割り当てていたため、既存 TOML を確認してください。新しい標準例へ移行する場合は旧設定をバックアップし、必要なモデルと推論強度を個別に反映します。ロール設定の切り戻しにはバックアップを復元します。有効化前に、プロジェクトやプラグインのスコープにも重複名がないことを確認します。
## v0.4.0・Python 管理版から v0.4.1 へ

同じ Codex 設定先と、有効リンク・旧スナップショット・ユーザーのロール TOML を保持します。現在の有効 ID を控え、v0.4.1 のバイナリで `nstack install --home "$config_dir" stage <新しいID>`、続いて `nstack install --home "$config_dir" activate <新しいID>` を実行します。切り戻しは v0.4.1 のバイナリで控えた ID を有効化します。CLI も戻す場合はその後に旧バイナリを選びます。v0.4.0 の Go インストーラーは v0.4.1 で取り除いたファイルを必要とするため、v0.4.1 の再有効化には v0.4.1 を使用します。

保存先とロックは共通です。Go で作成したスナップショットは全ファイルのチェックサムを照合し、チェックサムのない Python 版は旧版の必須ファイル・権限・スキルのメタデータと本文を確認します。旧スクリプトは実行しません。旧スナップショットを保持し、異なる版に同じ ID を使わないでください。v0.4.0 の OpenCode 環境でも、`--harness opencode` と[別の設定先](opencode.ja.md)を使って同じ手順で移行できます。
